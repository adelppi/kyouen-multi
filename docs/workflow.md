# 開発の進め方

Issue から PR までの進め方と、仕様とコードをそろえるための決まりを書く。人が作業するときも、AI が作業するときも同じ決まりに従う。

## 基本の考え方

- Issue 駆動: 作業は必ず Issue から始める。1つの Issue は1つの機能か1つの作業にし、1つの Issue に1つの PR を対応させる。
- ドキュメントが先: 1つの PR の中で、ドキュメントを先に書き、そのあとでソースコードを書く。
- 仕様駆動: `specs/` の仕様とソースコードは、どの時点でも食い違わないようにする。

## 作業の流れ

### 1. Issue を立てる

- `.github/ISSUE_TEMPLATE/task.md` の形で書く。
- 1つの Issue に複数の機能を入れない。大きい機能は、独立して PR にできる単位に分けて Issue を立てる。
- `vision.md` の「やらないこと」に当たらないかを確かめる。

### 2. ブランチを作る

- ブランチ名は `<Issue 番号>-<短い英語の名前>` にする（例: `12-room-create`）。
- `main` に直接コミットしない。

### 3. ドキュメントを書く

コードを書く前に、次の順にドキュメントを書いてコミットする。

1. `specs/` の該当する仕様を書くか、書き換える。新しい機能なら `specs/_template.md` を写して作る。
2. 書いている途中で決められないことが出たら、`open-questions.md` に追記する。
3. 何かを決めたら、`decisions/` に決定を追記する。
4. `vision.md` に関わる変更なら、`vision.md` も書き換える。

実装に必要な項目が未解決のままなら、その項目を推測で決めて実装に進まない。Issue か PR で決める人に尋ね、決まってから進む。

### 4. ソースコードを書く

- 仕様に書いた振る舞いだけを実装する。仕様にない振る舞いが要ると分かったら、先に仕様に書き足す。
- テストは仕様の受け入れ条件と対応させる。

### 5. PR を出す

- `.github/pull_request_template.md` の形で書く。
- 本文に `Closes #<Issue 番号>` を書く。
- コミットの順番は、ドキュメントのコミットが先、ソースコードのコミットが後にする。

### 6. レビューしてマージする

- 仕様とコードが食い違っていないかを確かめる。
- この PR で解決した未解決の項目が、`open-questions.md` で解決済みになり、決定へリンクしているかを確かめる。

## 仕様とコードをそろえる決まり

- コードの振る舞いを変える PR では、同じ PR で仕様も書き換える。仕様だけ、またはコードだけを変える PR はマージしない。
- ドキュメントだけを変える PR（誤字の修正、未解決の項目の追記など）はマージしてよい。
- 仕様とコードの食い違いを見つけたら、どちらに合わせるかが決まるまで `open-questions.md` に書く。決まったら、合わせる側を直す PR を出す。
- リファクタリングのように振る舞いを変えない PR では、仕様を変えなくてよい。

## AI が作業するとき

- 作業を始める前に `docs/README.md` の「読む順番」に従って読む。
- Issue の範囲を超える変更はしない。範囲の外で直したほうがよいものを見つけたら、新しい Issue の案として報告する。
- 決めるべきことを自分で決めない。選択肢と推奨を添えて `open-questions.md` に書き、尋ねる。
- `decisions/` の既存のファイルを消したり、本文を書き換えたりしない。
